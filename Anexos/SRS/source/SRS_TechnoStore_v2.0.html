1. Introducción

1.1 Propósito

Este documento establece los requisitos funcionales y de calidad de TechnoStore 2.0. Sirve como referencia para las personas responsables del desarrollo, validación, operación, mantenimiento y evaluación del producto.

1.2 Alcance del producto

TechnoStore es una aplicación web para consultar y administrar un catálogo de productos tecnológicos y gestionar el ciclo de una compra. Incluye cuentas de cliente, catálogo, carrito persistido, pedidos, inventario, personalización de la tienda, saldo digital de demostración, reportes, avisos por correo configurables y un módulo de errores y sugerencias.

El sistema no constituye una pasarela bancaria ni un servicio de dinero electrónico. La aplicación registra opciones de pago comerciales; el único pago que debita automáticamente un saldo es el saldo digital interno, expresamente simulado.

2. Descripción general

2.1 Contexto y arquitectura

La solución es una aplicación web cliente-servidor. El navegador presenta HTML, CSS y JavaScript clásico; el servidor procesa solicitudes PHP; MySQL/InnoDB mantiene las cuentas, productos y operaciones. La instalación de referencia del repositorio utiliza Apache, PHP y MySQL (por ejemplo, XAMPP).

La aplicación integra servicios externos para consultar países y sugerir ciudades. Las notificaciones de pedido utilizan SMTP cuando se habilita mediante configuración de entorno. La disponibilidad y las respuestas de esos proveedores no dependen de TechnoStore.

2.2 Clases de usuario

ActorNecesidades y permisos
VisitanteExplorar productos, buscar y filtrar el catálogo, ver detalles, términos y recursos públicos; registrarse o iniciar sesión.
Cliente autenticadoAdministrar su perfil y carrito; confirmar y consultar pedidos; gestionar su saldo de demostración; reportar errores y sugerencias.
Administrador autenticadoGestionar productos, categorías, existencias, pedidos, clientes, roles, elementos dados de baja, apariencia de la tienda y reportes.
Servicio externoProporcionar sugerencias de país o ciudad, o transportar notificaciones de correo cuando estén habilitadas.

2.3 Entorno y restricciones

  • El servidor requiere PHP con soporte PDO para MySQL y una base MySQL compatible con las restricciones y procedimientos almacenados del proyecto.
  • Las rutas de medios y anexos son relativas a la instalación web; el servidor debe servir el directorio de recursos configurado.
  • La interfaz necesita JavaScript habilitado. Las sugerencias de ubicación y el SMTP dependen de conectividad y configuración externas.
  • La moneda mostrada para los pedidos es el peso colombiano (COP).
  • El acceso a operaciones administrativas está condicionado por el rol ADMINISTRADOR mantenido en la sesión y validado en el backend.

2.4 Suposiciones y dependencias

  • Los operadores preparan y mantienen una instancia MySQL y configuran sus credenciales en el entorno del servidor.
  • Los administradores cargan productos, existencias, precios y medios; el sistema no valida la autenticidad comercial del inventario.
  • La consulta de países/ciudades puede no estar disponible si falla el proveedor externo; el formulario requiere valores válidos para completar la dirección.
  • Los documentos PAC, de calidad y los manuales se incorporan al proyecto copiándolos en sus carpetas designadas.

4.1 Retención y consistencia

  • La base de datos utiliza claves foráneas y restricciones para evitar relaciones huérfanas y cantidades, precios o saldos inválidos.
  • El precio unitario de cada línea queda congelado al confirmar la compra para mantener el valor histórico del pedido.
  • Las operaciones de confirmación, cobro con saldo y cancelación aplican transacciones para mantener coherentes stock, pedido y saldo.
  • Los elementos de catálogo y usuarios pueden conservarse mediante baja lógica para no romper el historial.
  • El backend incorpora columnas y tablas auxiliares durante las solicitudes; la migración es idempotente por sesión. La configuración de producción debe contar con permisos de migración de esquema.

5. Requisitos de interfaces externas

5.1 Interfaz de usuario

La aplicación se presenta en español y adapta sus vistas a los roles y la sesión. Los formularios muestran controles de validación y mensajes de operación; los modales y paneles exponen acciones identificables y se pueden cerrar mediante el teclado cuando así lo implementa la vista.

5.2 API interna

El cliente web intercambia datos con endpoints PHP mediante solicitudes HTTP y JSON/formularios. Las respuestas incluyen el resultado o un mensaje de error y un estado HTTP acorde con la solicitud. El identificador de usuario se obtiene de la sesión del servidor, no de un identificador libre enviado por el cliente para operaciones propias.

5.3 Servicios externos

  • REST Countries proporciona la lista de países cuando está disponible.
  • Nominatim/OpenStreetMap proporciona sugerencias de ciudades asociadas al país seleccionado.
  • Un servidor SMTP envía avisos de pedido solo si la variable MAIL_ENABLED y el resto de parámetros de correo están configurados.

7. Reglas de negocio y estados

  • Estados del pedido: CARRITO, PENDIENTE, PAGADO, ENVIADO, ENTREGADO y CANCELADO. CARRITO representa una compra aún no confirmada.
  • Un pedido confirmado consume existencias y guarda el precio unitario aplicado. Si falla el cobro digital, la transacción revierte los cambios relacionados.
  • Un cliente solo puede cancelar sus pedidos PENDIENTES. La cancelación administrativa permitida devuelve las unidades al stock; un pedido pagado con saldo digital también recibe el reembolso correspondiente.
  • Los medios Tarjeta crédito, PSE, Nequi y Contraentrega se guardan como método elegido, sin procesamiento de pago integrado en la aplicación.
  • El medio Dinero digital debita el saldo virtual al confirmar y crea un comprobante asociado al pedido.
  • Las bajas de productos, categorías y usuarios son lógicas; el borrado físico está restringido por relaciones de integridad.
  • Solo se puede restaurar un producto cuando su categoría está activa.
  • Los reportes de feedback pertenecen a una cuenta; la consulta administrativa muestra un máximo de 200 registros recientes y permite actualizar su estado.

8. Flujos principales y criterios de aceptación

8.1 Registro y acceso

  1. El visitante completa los campos obligatorios y acepta los términos.
  2. El servidor valida correo, longitudes y mínimo de contraseña y crea la cuenta con rol CLIENTE.
  3. La aplicación inicia la sesión del cliente y actualiza la navegación.
  4. Un correo inválido, una contraseña corta o la falta de aceptación debe impedir el registro y mostrar un mensaje.

8.2 Compra con saldo digital

  1. El cliente agrega un producto disponible al carrito y completa la dirección de entrega.
  2. Al confirmar, el servidor valida estado del carrito, cantidades y stock actual.
  3. El sistema congela los precios y descuenta las unidades dentro de una transacción.
  4. Con saldo suficiente, se registra el pago, se emite el comprobante y el pedido queda PAGADO.
  5. Con saldo insuficiente, se informa el error, se conserva íntegro el estado anterior del pedido y no se descuenta el stock.

8.3 Incorporación de anexos

  1. El responsable copia el documento compatible en la carpeta de su categoría: SRS, MER, PAC, herramientas de calidad o manual correspondiente.
  2. Al abrir el visor, el catálogo se consulta al servidor y la opción de la categoría permanece disponible aunque no existan documentos.
  3. Los PDF e imágenes permitidos ofrecen vista previa; los diagramas Draw.io ofrecen una vista interactiva y otros formatos se abren mediante su enlace.

9. Manejo de errores y límites

  • Una base de datos inaccesible impide completar operaciones que dependen de ella; el servidor devuelve un error y registra los detalles técnicos en el log.
  • El stock cambiante, los carritos vacíos, las direcciones incompletas, los permisos insuficientes y los datos inválidos deben detener la operación sin confirmar una compra parcial.
  • Si falla la consulta geográfica, las sugerencias pueden no estar disponibles. La integración externa no sustituye las validaciones obligatorias del pedido.
  • Los avisos por correo pueden no enviarse si SMTP está deshabilitado o no responde; el envío no reemplaza el registro del estado del pedido.
  • El módulo de feedback impide envíos vacíos, demasiado largos o superiores al límite por usuario y ventana temporal, e informa los fallos al solicitante.
  • El visor solo descubre archivos con extensiones permitidas en los directorios configurados; no publica scripts SQL ni recorre subdirectorios arbitrarios.

10. Alcance no implementado y asuntos por confirmar

Los siguientes elementos no deben considerarse funcionalidades entregadas por esta versión, a menos que se desarrollen y validen posteriormente:

  • Integración de cobro real con tarjetas, PSE, Nequi u otra pasarela; esos métodos no realizan cargos automáticos.
  • Seguimiento logístico en tiempo real, tarifas de transporte calculadas, transportadora integrada o tiempos de entrega garantizados.
  • Restablecimiento de contraseña por correo, autenticación multifactor, infraestructura de backups, monitoreo o SLA de producción.
  • Conversión o vista previa en navegador de todos los formatos Office; los documentos no previsualizados se ofrecen como enlace.
  • Políticas formales de retención, recuperación ante desastres y límites de rendimiento medidos; requieren definición operativa.

12. Aprobación y control de cambios

La versión 2.0 consolida los requisitos identificables en el producto y no altera el PDF SRS de versión 1.0. Los cambios posteriores deberán registrar una nueva versión y revisar sus criterios de aceptación, el modelo de datos y la implementación asociada.
